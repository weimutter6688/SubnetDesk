# 关闭 RDP 后首次连接短暂断开

关闭 Windows 远程桌面（RDP）窗口只会断开 RDP 连接，用户会话仍然存在。
Windows 可能先显示另一个登录会话，随后在恢复用户桌面时切回原会话。
SubnetDesk 的 Windows 后台服务会在目标会话中运行被控进程；目标会话变化时，
进程需要重新启动，现有 TCP 连接也会中断。因此第一次连接可能掉线，随后重连正常。

## 本机日志证据

2026-10-10 的服务、被控端日志与 Windows
`TerminalServices-LocalSessionManager/Operational` 事件可以对应起来：

| 时间 | 记录 |
| --- | --- |
| 18:49:55 | RDP 断开，后台服务从会话 1 切到会话 10。 |
| 18:50:40 | 接受第一次 SubnetDesk 连接。 |
| 18:50:42 | 登录响应完成，开始初始化画面。 |
| 18:50:48 | Windows 开始会话仲裁，会话 10 断开；原连接结束，记录 `os error 10093`。 |
| 18:50:48 | 服务尝试启动替代进程，记录 `os error 87`（参数错误）。 |
| 18:50:49 | Windows 将会话 1 重新连接到本地；服务记录 `session changed from 4294967295 to 1`。 |
| 18:50:50 | 第二次 SubnetDesk 连接登录成功。 |

`4294967295` 即 `u32::MAX` / `0xFFFFFFFF`，是 Windows 在控制台会话
暂时不可用时返回的标记，并非可以启动进程的会话编号。旧代码在服务循环的一个
分支中直接采用该值，先关闭原进程，再尝试在无效会话中启动替代进程。
`10093` 出现在已经成功登录的连接结束时，不能单凭它认定程序从未初始化 Winsock。

这些记录确认了本次断开与 Windows 会话迁移同时发生，另有无效会话处理缺陷。
它们不能证明其他机器或其他版本 RustDesk 的类似症状一定有相同原因。

## 修复与边界

服务现在忽略暂时不可用的会话编号，等待有效目标后再切换；同一会话的重复观察
不会触发重启。启动时若尚无有效会话，则先等待。启动被控进程前还有独立检查，
确保不会因为无效编号先关闭现有进程。轮询与 IPC 请求都使用相同的切换判断。

此修复避免无效目标造成的多余关闭与启动失败。真实的会话迁移仍可能结束原
被控进程；现有客户端会对已经建立的会话发生 `Reset by the peer` 等传输故障
自动重试。认证、设备指纹和主动断开仍按原有规则处理，不会绕过验证。
本次修复不提供跨 Windows 会话的 TCP 连接迁移，也不自动解除 Windows 锁屏。

本机检查时安装版仍为 `1.3.0+80`。测试与打包不会替换现有安装；应用修复需更新
被控端。包含 LAN 协议 v2 的新包需要控制端与被控端一起更新。

## 独立的视频编码故障

同一天 18:59:36 记录 `avcodec_send_frame failed`，19:00:06 记录
`stopped making progress in Encoding; restarting supervised server`。
这是编码线程连续 30 秒无进展后触发的恢复，与 18:50 的会话切换分开处理。
若持续出现，应进一步检查编码器和显卡驱动；本次会话修复不宣称解决该故障。

## 验证

```powershell
build\local-tools\native.cmd test --locked --offline --lib --features flutter,hwcodec,vram platform::windows::tests::service_ -- --test-threads=1
```

回归覆盖 `10 → 无有效会话 → 无有效会话 → 1` 的实际切换序列，以及启动时无
有效会话、有效 RDP 会话切换。测试只检查切换决策，不切换本机 Windows 会话。
真实验证需在更新两端后重复“关闭 RDP → 首次连接 → 恢复用户桌面”的步骤，
核对服务不再启动 `4294967295`，并确认客户端能在实际会话变化后恢复连接。
